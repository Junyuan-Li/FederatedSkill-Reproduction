## Reward semantics — critical

**reward = 1.0 is the ONLY "task passed" value.** Anything below 1.0 means the
task did NOT fully pass — the verifier's outer test failed. Fractional values
(0.5, 0.66, 0.9) are sub-test pass rates (partial-progress hint only, not
partial success).
- reward = 1.0 → covered (task passed) for that worker
- reward < 1.0 (ANY value) → NOT covered for that worker. Do not treat 0.5 or
  higher as "half-success".

Reward is per-(worker, model, task). A worker getting reward=1.0 does NOT mean
the workflow is covered for any other worker. Always interpret reward in
context of (worker_id, model, this round's task). A common misread to avoid:
"worker u1 got reward=1.0, so this workflow is covered, drop it" — wrong; only
u1 (and only u1's model) is confirmed covered. u0/u2 are unconfirmed, and if
their patches have reward<1.0 the workflow is likely still a gap for their
models specifically.

## Capability matrix cell states (four states — do not invent others)

Combine this round's patch reward for worker W with whether W's pre-task
library already has a skill whose description matches the workflow:

| this round's patch reward (worker W) | W has a matching library skill? | meaning | matrix action |
|---|---|---|---|
| 1.0 | yes | W passed, library skill works | mark `covered` for W; drop the workflow entirely only once ALL workers are `covered` |
| 1.0 | no, but this round's patch adds a matching skill | absorbing — will be covered once Stage2 merges the patch | mark `absorbing` for W |
| < 1.0 (e.g. 0.0, 0.5, 0.66, 0.9) | no | workflow NOT passed; library lacks it | mark `gap` for W; state what is missing, citing the actual reward value |
| < 1.0 | yes | library has the skill but it is broken or wrong-grain | mark `broken` (gap) for W; Stage2 must repair the existing skill, not bypass it with a new one |
| not attempted this round | — | carry over | keep the prior state unchanged |

Edge cases: a patch reward=1.0 that *replaces* a library skill at the same
name keeps that worker `covered`. A library skill whose description matches
closely but reward is 0 — check whether the worker's patch/summary shows it
actually invoked that skill; sometimes workers ignore their own library and
the skill isn't really tested. A **persistent gap** — the same worker stuck at
`gap`/`broken` for 3+ rounds while peers are `covered` — is the cross-model
contamination signal: flag it explicitly and prefer a `refactor` directive
scoped to that worker's own model rather than another `absorb` of a peer
skill that has already failed to transfer.

## Per-worker findings — only for workers with REAL gaps; only based on FACTS

Write detailed per-worker findings **only** for workers with one or more
`gap`/`broken` cells this round. For workers whose every workflow is
`covered`, keep it to a single line: "worker uN (model): stable, do not
over-engineer" — do not invent weaknesses to justify a change. (Detailed
findings for an otherwise-stable worker are a known regression trigger: Stage2
tries to fix what isn't broken and breaks the working library.)

**Evidence rule — record facts, don't speculate.** Every claim must cite a
specific round and the literal reward observed. Forbidden: "this worker is
volatile" without citing rounds; "this worker fails on new input formats" from
a single round; inventing a workaround whose effectiveness has not been
demonstrated. A pattern claim ("this worker has a pattern of writing inline
Python instead of using the skill") requires **≥2 rounds of evidence** cited
in parentheses — a single round is "observed in round N", not a pattern.
Workarounds proposed for Stage2 must be phrased as hypotheses ("hypothesis:
try X") not asserted fixes — the next round's evidence will confirm or refute.

## Directive construction (for the `directives` field)

For each worker with a `gap`/`broken`/`absorbing` cell, propose at most one
directive per workflow:
- **absorb** — a peer's (or this worker's own) patch has reward=1.0 and
  supplies the missing/matching skill; apply it, citing `source_worker_id`
  and `source_reward`.
- **repair** — the worker's own library already has a matching skill but it
  is broken (reward<1.0 despite a matching skill); fix in place, no peer
  source needed.
- **refactor** — persistent gap for this worker's own model even though
  peers/self have reward=1.0 elsewhere; rewrite specifically for this
  worker's model/CLI rather than copying a peer's skill verbatim.
- **no_update** — covered, or no actionable evidence yet; do not force a
  directive just to produce output. Do not silently default an unrecognized
  or unjustifiable action to `absorb`.
Priority (1 = highest) should reflect how many rounds a gap has persisted and
how many workers are still blocked by it.

## What to avoid

- Vague gap reasons ("gap") without citing what specifically failed (script
  bug, missing helper, format mismatch, the actual reward value).
- Vague per-worker notes ("this worker has model-specific issues") without a
  concrete, cited behavior.
- A per-round event journal ("round 3: worker did X, round 4: worker did Y")
  — compress into a standing pattern with the supporting rounds cited in
  parentheses.
- Dropping a workflow from the matrix while ANY worker still has a gap —
  partial coverage stays recorded until every worker is `covered`.
