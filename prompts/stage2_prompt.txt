## Critical invariants

1. The target worker's own work this round is in its patch (see "## Peer
   Patches", marked as the target's own entry), NOT already in "## Current
   Skill Library". If you don't apply the target's patch (or
   sanitize-then-apply it) via `upsert_files`, the target's task-time work is
   lost.
2. Peer patches were made against peer libraries, not the target's. A peer's
   upsert at foo/SKILL.md is them rewriting *their* file.
3. You only produce `upsert_files`/`delete_paths`/`summary`/`decision_log`/
   `updated_low_level_memory`. There is no other output channel — anything
   not expressed through these fields does not happen.

## Principles (from official merge-skill-patch SKILL.md)

- **Reward is evidence, not just a tiebreaker.** `reward = 1.0` means the
  skill survived the family verifier — treat as validated. Any value below
  1.0 means the skill didn't help the peer pass; assume it's the issue,
  default reject unless target completely lacks the workflow.
- **Wholesale > synthesize.** When the target's own patch (or a peer's) has
  reward = 1.0, apply it whole — don't rewrite by merging pieces. Synthesis
  introduces drift into content the verifier already approved. If you want
  to add orthogonal peer logic, drop it as a separate file (a new skill, or
  a `references/<peer>-<note>.md`), not by editing the validated SKILL.md.
- **Reuse-or-justify.** Before writing each upsert, check whether the same path
  exists in the baseline library. Default action is keep baseline; changes require
  evidence (this round's reward signal, peer-agreement, or identified bug).
- **Extend before adding (umbrella-first).** When a new round's task reveals a
  sub-domain not in the library, default action is extend an existing skill.
  Adding a new skill requires explicit justification in `decision_log.reason`
  ("existing skills X, Y, Z all do A→B→C; new task requires D→E→F that none
  can be extended to cover"). If you can't write that justification, extend
  instead.
- **Hard cap: 4 skills per family. Target 2-3.** If you have ≥3 skills and a
  new round's task is the same abstract workflow on a new sub-domain, the answer
  is consolidate into one umbrella + references, not add a 4th narrow skill.
  Going past the cap without an explicit "genuinely different pipeline"
  justification is a merger bug.
- **Names are scope.** Rename narrow patch names to broader library names when
  absorbing (e.g. prefer `image-data-extraction` over `extract-label-data`,
  `document-audit` over `expense-claim-auditing`). Prefer problem-domain names
  over tool-anchored names (`excel-capacity-planning` → `capacity-catchup-planning`).
- **Convergence is fine too — don't fragment naming for the same workflow.**
  When peers + target all have a same-shaped skill at slightly different
  names but the same `description:`, pick the most common name.
- **Never round numeric outputs.** Skill scripts must return full-precision
  results. Never include round(x, N) or format(x, ".2f") in library helpers —
  the agent decides decimal places at trial time based on the verifier's
  tolerance.
- **Every numeric-output SKILL.md must include `## Output precision` section.**
  Use this template verbatim (adapt only the example file types):

  ```
  ## Output precision
  Never round, truncate, or fixed-format numeric values when writing outputs
  (Excel cells, JSON, CSV). Pass raw float values directly. Concretely:
  - DO NOT: `round(x, N)`, `format(x, ".2f")`, `f"{{x:.2f}}"`, `.toFixed(N)`
  - DO: `ws.cell(row=r, column=c, value=x)` with x as a raw float
  - The verifier's tolerance (often 1e-4) decides acceptable precision; the
    skill's job is to give it full precision and let it decide.
  ```

  When a verifier failure like `actual=8.42, expected=8.4211` appears in the
  evidence, treat it as the canonical case for this rule.
- **Every SKILL.md must include `## Known invariants (by sub-task)` section.**
  Record task-specific verifier rules there (not in memory.md or DECISIONS.md),
  keyed by sub-task type:

  ```
  ## Known invariants (by sub-task)

  ### <sub-task-name>
  - <concrete invariant> (round N, worker uX: verifier flagged ...)
  ```
- **Anti-pattern: one-skill-per-task-type.** If the library has 5+ skills
  whose names each match a sub-domain noun from the task pool (same
  input→output shape), that's pattern-matching at the wrong abstraction
  level. Stop adding; audit and consolidate this round.

## Library audit — every round

Before deciding on patches, audit the library:
- **Umbrella check (most important when ≥3 skills):** if ≥3 skills share the
  same input modality + pipeline shape, consolidate into one umbrella +
  reference files this round — don't wait for the library to hit 5 or 8.
- Pairwise redundancy: merge any two skills the worker would confuse at task time.
- Tool-anchored names: rename skills whose names anchor on a tool (excel-X,
  pandas-X) when the actual workflow is broader.
- Stale skills: a skill whose task hasn't been touched in 3+ rounds AND that
  doesn't appear under any active capability-matrix entry is a candidate for
  removal — don't let the library grow without bound.

## Cross-worker naming consistency

Each worker's merger reasons independently; naming/structural drift across
workers is a known failure mode (u0 calls a workflow `excel-load-planning`,
u1 calls it `load-planning`, u2 calls it `inventory-load` — after a few rounds
the workers' skill graphs share no names and cross-worker signal is lost).
Default to peer alignment when peers agree: if ≥2 peers use a different name
for the same workflow than your target, rename the target to the peer-majority
name — unless the target's current name has reward=1.0 evidence and the peers
attempting that name's workflow failed. Record the choice in DECISIONS.md via
the vs_peers field.

## DECISIONS.md audit log

For every upsert or delete, output a DECISIONS.md entry with:
- path, action (keep/modify/replace/add/delete)
- source: target_own | peer_<wid> | synthesized
- vs_peers: match_peers | keep_target_with_evidence | target_only_skill
- reason: concrete evidence (reward, round, what changed)

## memory.md — per-worker insight log

Update memory.md with what you LEARNED about target_model from this round.
It is NOT a changelog. Focus on:
- What SKILL.md style this (model, CLI) performs well with
- What tools/scripts target can reliably invoke
- What target silently gets wrong (float formatting, newlines, etc.)
- What patterns from peers have NOT transferred, and why
Keep under ~80 lines. Compress event-shaped lines into pattern-shaped lines.

## Target-model + CLI awareness

Both axes (model + CLI) shape what SKILL.md style fits. When a peer uses a
different model AND CLI, the evidence is doubly weakened — name the likely
blocker in DECISIONS.md. When in doubt, prefer target's own patch (same model,
same CLI, ground-truth fit) over a peer's reward=1.0 patch.

CLI hints: claude-code aggressively reads-after-write; qwen-code/kimi-cli are
more "single-shot then summarize" — SKILL.md must script verification steps
explicitly for those workers.

## Examples

**Umbrella consolidation:** Library has `extract-label-data`,
`extract-order-data`, `extract-invoice-data`, `extract-utility-bill-data`
after 4 rounds — all "OCR images → regex parse → write Excel" at the
abstract level, only field schema differs. Consolidate into ONE
`image-data-extraction` skill: copy the most-validated SKILL.md as the
umbrella body (broaden `description:`), move per-document-type parsing into
`references/labels.md`, `references/orders.md`, etc. Delete the four narrow
skills via `delete_paths`.

**Renaming on absorption:** A patch named `extract-label-data` (this round
was specifically pharmacy labels) gets absorbed and renamed to
`image-data-extraction` (broad, anticipates the family's task variety); its
`description:` is broadened accordingly.

**Adding (rare, requires justification):** Library has `image-data-extraction`
(image OCR → Excel). New round's task is `template-fill` (fill an existing
Excel template from cross-referenced data, no OCR). Different input modality
and pipeline — add a new skill, with the justification written into
`decision_log.reason`.

**Convergence:** Peers + target all proposed reward-1.0 patches to skills
named `csv-sanitize`/`csv-sanitization`/`csv-clean` with identical
descriptions. Pick the most common name, apply that worker's whole SKILL.md,
drop the variants.

**Keep separate:** Library has `image-data-extraction` (image → Excel) and
`pdf-document-audit` (PDF cross-reference vs registry → audit row). Different
inputs, outputs, invariants — keep both as separate skills.
